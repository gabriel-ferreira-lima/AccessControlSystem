# Tarefas: Segurança do perímetro (console web e entrada de dados da Api)

**Entrada**: Documentos de design em `/specs/20261102-125831-security-perimeter/`

**Pré-requisitos**: [plan.md](plan.md), [spec.md](spec.md), [research.md](research.md), [data-model.md](data-model.md), [contracts/](contracts/), [quickstart.md](quickstart.md)

**Testes**: obrigatórios (Princípio VII, TDD). Em toda fase os testes vêm **antes** da implementação, cada tarefa de teste diz o que deve falhar (Red) e por quê, e o Red é **visto** e anotado antes do Green. "Red por não compilar" só vale como primeiro passo; onde o Red de **comportamento** depende de tipos novos, uma tarefa de **ESQUELETO MÍNIMO** cria antes os tipos sem comportamento, para tudo compilar. A Fase B é a exceção honesta: ela **prova** um comportamento que já existe (o `acs_app` já está correto), e o Red dela é o teste dos **papéis-canário** (a sonda precisa acusar um privilégio a mais). **Nenhuma tarefa comenta, apaga ou desliga teste.**

**Organização**: por **fase**, exatamente as do plano (0, A, B, C, D), cada uma terminando num **checkpoint** com build e testes verdes, para revisão e commit separados (a Fase 0 é só medição e não tem checkpoint com parada). Rótulos de história da spec: **[US1]** tamanho máximo na entrada · **[US2]** cabeçalhos do console · **[US3]** HSTS · **[US4]** prova do usuário de banco · **[US5]** CI de pacotes. Mapa: Fase A = US1 · Fase B = US4 · Fase C = US2 + US3 · Fase D = US5.

## Formato: `[ID] [P?] [Story] Descrição`

- **[P]**: pode rodar em paralelo (arquivos diferentes, sem dependência de tarefa incompleta).
- Caminhos relativos à raiz do repositório. `Api`, `Application`, `Domain`, `Infrastructure` e `Tests` abreviam `src/Backend/AccessControlSystem.{Api,Application,Domain,Infrastructure,Tests}`; `Front` abrevia `src/Frontend`.
- `FX-nn` aponta uma linha de **"Ajustes de fixture"** (no fim). **Nenhuma tarefa está marcada como concluída.**

## Regras fixas (valem para todas as tarefas)

1. **Sem commits.** O agente não faz commit nem push. Cada checkpoint é um ponto de revisão e de commit **separado**, feito pelo revisor.
2. **Parada em cada checkpoint.** A **Fase 0 não para**: mede, anota e segue direto para a Fase A. Os checkpoints com parada são **A, B, C e D**: parar, preencher a tabela "Registro de números", reportar os números e a lista de arquivos alterados (`git status --short`), e aguardar o commit do revisor antes de seguir. O **primeiro** commit é o do checkpoint A e leva a linha de base (commit "0 + A").
3. **Integridade das entregas** (constituição): não apague, pule nem enfraqueça teste. **Nenhum teste existente é alterado**: a tabela "Testes existentes afetados" está vazia de propósito (verificado, com a razão), e a tabela seguinte lista os arquivos existentes que só **recebem métodos novos**. Se um teste existente precisar mudar, ou qualquer verificação falhar, **pare e reporte a saída real**. Nenhum `Skip`, nenhum aviso suprimido (a única supressão é a do `SSH.NET`, T058, que **substitui** a que já existia).
4. **Edição**: use as ferramentas de edição (preservam CRLF e acentos em UTF-8). **Nunca** `sed -i` em arquivo versionado: o `sed` do Git Bash descarta o `CR` dos arquivos CRLF. Arquivos `.sh` são LF (`.gitattributes`).
5. **Migrations**: esta spec **não tem migration** e **nenhuma tarefa roda `dotnet ef`** (a `SeedAdmin` criaria o administrador de senha fixa numa base nova).
6. **Pacotes**: **nenhum pacote novo** (NuGet ou npm). A **única** mudança de versão é a correção das vulnerabilidades do front (T063–T064: `vite` e `source-map-js`, na mesma major). Se o `npm audit fix` (T063) pedir `--force`, **parar e reportar**.
7. **Sem estático novo**: `ContractExtensions` é classe estática **sem campo** (`NoStaticTenantStateTests` continua verde sem alteração).
8. **Constituição e `.env` do dono não são tocados.** A proposta de emenda (R-12) é pendência do dono do projeto.
9. **Gates canônicos**:
   - **GATE-BACK**: `cd src/Backend && dotnet build Backend.slnx && dotnet test Backend.slnx` (Docker ligado). Esperado: `0 Aviso(s)`, `0 Erro(s)`, `Com falha: 0`, `Ignorado: 0`.
   - **GATE-FRONT**: `cd src/Frontend && npm run typecheck && npm test && npm run build`. Esperado: tudo verde, 0 falhas.
   - **Só rápidos**: `dotnet test Backend.slnx --filter "Category!=Integration"`.
   - **Todo checkpoint roda os dois gates** (mesmo quando a fase não toca um dos lados): é a prova de que nada anterior quebrou (SC-011).
10. **Esqueleto mínimo (tarefas marcadas ESQUELETO)**: só tipos, assinaturas e **constantes de valor definitivo**, sem o comportamento novo. Cada arquivo ou trecho de esqueleto leva o comentário `// ESQUELETO (security-perimeter): substituir na tarefa Txxx`, **removido** na tarefa de implementação; a varredura T071 exige zero ocorrências de `ESQUELETO`.
11. **Papéis de banco são do cluster inteiro**, não do banco isolado. Todo papel criado por um teste (canários, Fase B) tem **nome único por execução** (`canary_<tipo>_<Guid:N>`), é criado **sem LOGIN** e é **removido no `DisposeAsync`**, mesmo se a asserção falhar: antes do `DROP ROLE`, rodar `REASSIGN OWNED BY` e `DROP OWNED BY` em **cada banco** onde o papel recebeu algo (`DROP ROLE` falha com "role cannot be dropped because some objects depend on it"). Nenhum teste altera o `acs_app` nem o `acs_migrator`.
12. **FR-030 (PRs em rascunho com pacote vulnerável) NÃO é tarefa do implementador**: exige push e PR no GitHub. É **validação do revisor depois do push** (seção "Validações do revisor", V-01 e V-02). O implementador entrega só a configuração que faz o CI ficar vermelho (Fase D) e a prova local equivalente (T057, T055).

## Estratégia de implementação

1. **MVP**: Fase A (US1, P1) sozinha já fecha o vetor de negação de serviço mais barato; as Fases B, C e D são independentes entre si em código e entregam cada uma o seu valor.
2. **Entrega incremental**: um commit e uma revisão por checkpoint; a `main` só recebe o conjunto por PR com o CI verde.
3. **Parada obrigatória** em qualquer verificação que falhe, em achado de permissão a mais no `acs_app` (T034), em `npm audit fix` que peça `--force` (T063) e em necessidade de alterar um teste existente.
