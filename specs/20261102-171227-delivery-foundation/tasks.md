# Tarefas: Base de entrega sem nuvem

**Entrada**: Documentos de design em `/specs/20261102-171227-delivery-foundation/`

**Pré-requisitos**: [plan.md](plan.md), [spec.md](spec.md), [research.md](research.md), [data-model.md](data-model.md), [contracts/](contracts/), [quickstart.md](quickstart.md)

**Testes**: obrigatórios (Princípio VII, TDD). Em toda fase os testes vêm **antes** da implementação, cada tarefa de teste diz o que deve falhar (Red) e por quê, e o Red é **visto** e anotado antes do Green. Onde o Red de **comportamento** depende de tipos novos, uma tarefa de **ESQUELETO MÍNIMO** cria antes os tipos sem comportamento, para tudo compilar; onde o teste falha porque o arquivo (script, workflow) ainda não existe, isso já é o Red. **Nenhuma tarefa comenta, apaga ou desliga teste.**

**Organização**: por **fase**, exatamente as do plano (0, A, B, C, D, E). **Cada fase de código (A a D) termina num checkpoint com build e testes verdes (GATE-BACK e GATE-FRONT), para revisão e commit separados pelo revisor.** A Fase E é **manual**: a primeira tarefa é do **revisor** (validar o gate no GitHub real, depois do merge e **antes** de aplicar o ruleset) e as demais são do **dono**. Rótulos de história da spec: **[US1]** principal só aceita mudança verificada · **[US2]** verificação agregadora · **[US3]** fork sem segredos · **[US4]** auditoria de pacotes agendada · **[US5]** saúde da Api · **[US6]** dados fictícios de homologação · **[US7]** verificação do administrador fixo · **[US8]** conferência e guia das proteções. Mapa: Fase A = US5 · Fase B = US6 + US7 · Fase C = US2 + US3 + US4 + conferência automática (US8) + pós-merge (FR-013a) · Fase D = US1 + US8 · Fase E = US1 + US8 (manual).

## Formato: `[ID] [P?] [Story] Descrição`

- **[P]**: pode rodar em paralelo (arquivos diferentes, sem dependência de tarefa incompleta).
- Caminhos relativos à raiz do repositório. `Api`, `Migrator`, `Infrastructure` e `Tests` abreviam `src/Backend/AccessControlSystem.{Api,Migrator,Infrastructure,Tests}`; `Front` abrevia `src/Frontend`.
- **`[MANUAL DO DONO]`** marca tarefa que **só o dono** executa, no GitHub real (o implementador **não** a executa nem a marca como concluída).
- **`[REVISOR]`** marca tarefa que **só o revisor** executa, no GitHub real, **depois do merge** (o implementador **não** a executa nem a marca como concluída).
- **Nenhuma tarefa está marcada como concluída.**

## Regras fixas (valem para todas as tarefas)

1. **Sem commits.** O agente não faz commit nem push. Cada checkpoint é um ponto de revisão e de commit **separado**, feito pelo revisor (um commit por fase A, B, C e D; o primeiro leva a linha de base: commit "0 + A"). Um só pull request reúne A a D. **Anotar o `HEAD`** (`git rev-parse --short HEAD`) em T003 e de novo ao retomar depois de cada commit do revisor: a conferência de "nenhum commit do agente" (T064) compara com esse `HEAD` anotado, e não com um commit fixo.
2. **Parada em cada checkpoint.** A **Fase 0 não para**: mede, anota e segue para a Fase A. Os checkpoints **A, B, C e D** exigem: GATE-BACK e GATE-FRONT **verdes** (o GATE-FRONT inclui o `npm audit`, com o resultado anotado), preencher a tabela "Registro de números", reportar os números e a lista de arquivos alterados (`git status --short`), e **aguardar o commit do revisor** antes de seguir.
3. **Integridade das entregas** (constituição): não apague, pule nem enfraqueça teste. **Nenhum teste existente é alterado**: a tabela "Testes existentes afetados" está vazia de propósito (com a justificativa do R-20), e a tabela seguinte lista os arquivos existentes que só **recebem métodos novos**. Se um teste existente precisar mudar, ou qualquer verificação falhar, **pare e reporte a saída real**. Nenhum `Skip`, nenhum aviso suprimido.
4. **Edição**: use as ferramentas de edição (preservam CRLF e acentos em UTF-8). **Nunca** `sed -i` em arquivo versionado (o `sed` do Git Bash descarta o `CR`). Arquivos `.sh` são LF (`.gitattributes`).
5. **Migrations**: esta spec **não tem migration** e **nenhuma tarefa roda `dotnet ef`** (a `SeedAdmin` criaria o administrador de senha fixa numa base nova). Verbos do Migrator só por `MigratorApplication.RunAsync` nos testes ou `docker compose run --rm migrator ...`.
6. **Pacotes**: **nenhum pacote novo** (NuGet ou npm) e **nenhuma ação de terceiros** nos workflows (só `actions/*` e chamadas locais `./.github/workflows/...`).
7. **O implementador não toca o GitHub real.** Nenhuma tarefa de A a D roda `gh` de verdade, `git push`, abre PR, aplica o ruleset nem ensaia a proteção. Os scripts de `scripts/github/` são testados com um **`gh` falso** (`GH_BIN`, T052) e **nunca** executados com o `gh` do dono. A validação do gate com PRs descartáveis (**[REVISOR]**), a aplicação, a conferência real e os ensaios são a **Fase E, depois do merge**.
8. **Testes que rodam script** usam **só** `ScriptShell`/`BashLocator` (T030 a T033): no **Windows**, `bash` = variável `ACS_BASH` (se definida) senão `C:\Program Files\Git\bin\bash.exe`, **nunca** o `bash` do PATH (lá é o atalho do WSL, recusado); no **Linux**, `bash` do PATH. Sem `bash` ou sem `jq` (procurado **dentro** do `bash` escolhido) o teste **falha com mensagem clara, nunca pula**. Scripts rodam com o diretório de trabalho na **raiz** e **caminho relativo**. **Arquivos temporários** dos testes de script (o `gh` falso e o arquivo do `$GITHUB_STEP_SUMMARY`) ficam em `ScriptShell.NewScratchDirectory()` = `src/Backend/AccessControlSystem.Tests/obj/script-tests/<Guid>/`: caminho **relativo à raiz**, igual para o Git Bash e para o .NET, e **ignorado pelo git** (o `src/Backend/.gitignore` ignora `[Oo]bj/`; o `obj/` da **raiz não** é ignorado, por isso não serve). Escolha registrada aqui (I8).
9. **Tudo que os testes usam é `public`** (não há `InternalsVisibleTo`): `ICatalogProbe`, `CatalogReadinessHealthCheck`, `SeedAdminFingerprint`, `FixedAdminVerifier`, os comandos e as opções novas.
10. **Gates canônicos**:
    - **GATE-BACK**: `cd src/Backend && dotnet build Backend.slnx && dotnet test Backend.slnx` (Docker ligado). Esperado: `0 Aviso(s)`, `0 Erro(s)`, `Com falha: 0`, `Ignorado: 0` **e código de saída 0** (conferir o `exit`, não só a linha-resumo: falha de limpeza de coleção sai com "Com falha: 0" e `exit=1`).
    - **GATE-FRONT**: `cd src/Frontend && npm run typecheck && npm test && npm run build && npm audit`. Esperado: tudo verde, 0 falhas e `npm audit` sem vulnerabilidades (o front só muda em documentação, mas o gate prova que nada quebrou, SC-013, e que não há pacote vulnerável: a constituição exige o `npm audit` antes do PR, sempre). **Anotar o resultado do `npm audit`** em cada checkpoint; se aparecer vulnerabilidade, **parar e reportar** (nunca suprimir o aviso).
    - **Só rápidos**: `dotnet test Backend.slnx --filter "Category!=Integration"`.
    - Se o `docker compose up --build` falhar com EOF ao resolver `mcr.microsoft.com`, rodar `docker pull` das imagens base (`sdk`, `aspnet`, `runtime` 10.0) e repetir.
11. **Esqueleto mínimo (tarefas ESQUELETO)**: só tipos, assinaturas e constantes de valor definitivo, sem o comportamento novo. Cada arquivo ou trecho leva `// ESQUELETO (delivery-foundation): substituir na tarefa Txxx`, **removido** na tarefa de implementação; a varredura T064 exige zero ocorrências em código.
12. **Nada contra a constituição e o `.env` do dono**: a constituição e o `.env` não são tocados.
13. **Erros de segurança**: se o `gh` falso, um teste ou qualquer saída mostrar **segredo, senha, e-mail de operador ou identificador do administrador fixo na saída dos verbos**, parar e reportar.
14. **Nomes de teste**: todo método de teste novo é uma **frase em português com underscore**, no estilo do que já existe (por exemplo `Sai_com_2_com_configuracao_invalida`); nos `[Theory]` em tabela, os nomes de caso são curtos.

## Estratégia de implementação

1. **MVP**: a **Fase C** (gate, auditoria e conferência) é o que mais protege cedo, mas só vale depois de aplicada (Fase E). Por isso a ordem do plano é A, B, C, D e só então E: a proteção é ligada **depois** de o gate existir na `main`.
2. **Entrega incremental**: um commit e uma revisão por checkpoint; um só pull request (A a D) entra **sem** proteção (a `main` ainda não tem ruleset). Depois do merge, o revisor valida o gate com PRs descartáveis (T066) e, **só então**, o dono aplica o ruleset; correções do gate encontradas em T066 entram por PR pequeno ainda sem proteção. A `main` só recebe o conjunto por PR com o CI verde.
3. **Parada obrigatória** em qualquer verificação que falhe, em necessidade de alterar um teste existente, em segredo ou e-mail de operador aparecendo na saída (regra 13), em `jq` ou Git Bash ausentes (T003) e em qualquer tentativa de tocar o GitHub real antes da Fase E.
